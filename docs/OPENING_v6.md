## 3. 任务顺序（「好好修一下」= 先修调度，再全算力打）

### ① 先把每步墙钟构成量清楚（先做，不写新机制）
把 v5 的 240 局 step 数据全量拉下来（`data/_v5_lockscan.py` 改 label 即用），按 **pre-lock 扫描 / pool 搜索 / tail / worlds** 分层，
统计每类步的 ms 分布、over 出在哪些步、每步**实际用掉多少预算**（v5 用了 7s 预算里的多少）。
输出 `out/_v6_budget.json` + 一张分层表。**没有这张表不要动参数。**

### ② 修 v5b 暴露的调度 bug：波次准入控制
v5b 失败机制：每波提交后如果剩余时间不足一次搜索，最后一波会被 deadline 截断 → `status≠0` → RoutePool 不采纳 = 白烧，
over 8→57。修法：**发波前要求 `left ≥ 单次搜索预期耗时 + 安全余量`**（用滑窗估计单次耗时），并把 `search_deadline_cap`
从 4.0s 降到「单次预期 × 1.5」。**修好后 waves 上限不再重要，改成「预算内自适应波数」**（目标：不增 over 的前提下
把 12 起点提到 20–30）。

### ③ 并行/线程配比（把 24 核吃满）
量 native `policy_search` 的线程扩展（1/2/4/8 线程的 transitions/s）与 **scan 子进程（procs=16）在 parallel 5-6 时的饥饿**；
定「parallel_games × threads_per_game ≈ 20」的配比（现在 5×4=20 已接近，但 pre-lock 的 16 路扫描会抢核 → 考虑 pre-lock
阶段降低 threads / 提高 scan 优先级）。**这是「每墙钟秒吞吐」的直接杠杆。**

### ④ 策略引导起点（单调安全的新臂）
B11 的 policy/advantage 网（`data/knowledge/ei_policy_v6.json`）作为 **GNRPA prior 只挂在部分波次**上（历史全局 prior 全负，
但作为**多起点之一**由 RoutePool 取 max = 单调安全）。实现：`RoutePool(prior=self.pr)` 已支持，给某些 wave 开 `use_prior`。
门：同题同 seed 配对 8–10 槽，看有没有稳定增益（预期小但便宜）。

### ⑤ 精确尾 horizon（tail_turns 2→3 可行性）
先测：剩 3 回合时 tail_exact（threads 8/16、node_cap 20M、8s）能否 `complete`；当前深局 2 回合已常 deadline。
若 3 回合能在 8s 内 complete → 直接 +1 回合的最优，决赛大槽收益大；否则只保留 2 回合。

### ⑥ 独立可攻点（不依赖上面）
`lock≥4` 的 11 槽（v4 均分 588k）+ 8 个**无 oracle 的 produce-008 低分槽**（400–870k，v4 只锁上没打高）；
先看这 19 槽的 step 数据（锁晚了？候选/投票没跟上？）再定机制。

## 4. 算力与托管策略（「全部算力跑下一把」）

- 一把全量 240 槽的实测成本：**v5 = 4,138s（69min，parallel 5 / waves 2）；v5b = 8,706s（145min，parallel 5 / waves 3）**。
  ⇒ 下一把建议 **parallel 5–6 + 自适应波数（预算内 20–30 起点）**，预计 90–120min。
- 顺序：**①②③ 修完先跑 20–30 槽的小样**（挑 10–15 个大决赛槽 + 3–5 个 MID），同槽对 v5/v4 看 Δ 和 over，
  通过后再**一把全量 240**。**不要用全量跑去试参数**（一把 2h）。
- 判据（沿用）：**只看 240 槽聚合**（单槽同 config 重跑 ±5–7%、大槽 ±20%）；逐槽配对 + oracle 比例 + over 三项一起看。
